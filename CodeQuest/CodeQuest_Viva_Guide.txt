No server. Perfect for a college desktop project. Python already has `sqlite3`.Why not MySQL?MySQL needs installing a server, username, port. For a single PC quiz, that is extra work. SQLite is enough.Why local database?Privacy, offline lab viva, no hosting cost. File is `codequest.db` next to the app.Why password hashing?If someone copies the db file, they should not read the real password. We store a hash, not `password123`.What is PBKDF2?It is a slow hashing method. I use SHA-256 inside it, 120,000 rounds, plus a random salt. Slow is good, because hackers cannot try millions of passwords quickly. Salt means two users with the same password get different stored values.Stored format: `salt$hexdigest`. Compare uses `secrets.compare_digest` so timing is safer than normal `==`.Why foreign keys?Child rows must belong to a real user. I turn them on with `PRAGMA foreign_keys = ON` every connection, because SQLite does not enforce them unless you do that.Why ON DELETE CASCADE?If I delete a user, stats, settings, progress, achievements go with them. No orphan rows. Leaderboard uses SET NULL so a high score name can remain even if the account is gone, except delete-account also removes that name on purpose.Why UNIQUE constraints?Username unique: no two accounts with same name.Progress unique on (user, language, level): one score per level path.Achievement unique on (user, badge).Leaderboard unique on name: one best score per player.Tablesusers, stats, settings, progress, achievements, leaderboard, meta (migration flag).---Step 5 – ER DiagramThink: User is the parent. Everything else is the child, except leaderboard is a bit special.1. users → statsParent: usersChild: statsType: 1 to 1 (`user_id` is primary key in stats)Why: One stats row per accountExample: Vinit has 10 games played. That number lives in stats, linked by his id.2. users → settingsType: 1 to 1Why: Sound and timer are personalExample: Vinit turns timer off; Rohit keeps it on.3. users → progressType: 1 to manyWhy: Many language-level scoresExample: Python level 1 score 4, Java level 2 score 3.4. users → achievementsType: 1 to manyWhy: Many badges over timeExample: Perfect Score, then Expert later.5. users → leaderboardType: 1 to 0 or 1 (user_id can be NULL)ON DELETE SET NULLWhy: Board is public ranking by name; user might be deletedExample: Name “Vinit” with best 5/5.Memory trick: User owns a profile bag (stats + settings) and a backpack of many items (progress + badges). The school notice board (leaderboard) shows names, not only ids.---Step 6 – Architecture```User  ↓GUI (ui.py, theme.py, splash.py)  ↓Application Logic (game.py, achievements.py, rank.py, stats.py, ...)  ↓SQLite Database (database.py → codequest.db)```User: You click Login, pick Python, tap an answer.GUI: The window you see. Extra +50 XP on result if score is 5 (`ui.show_result`). Shop XP booster +50. Rank/level from XP via `rank.get_rank` and `xp_to_level`.Unlock achievementResult screen → `achievements.check` → `unlock_achievements` INSERT OR IGNORE.Leaderboard updatesResult → `leaderboard.save(name, score)` → upsert by name, keep max best_score, trim to 10.LogoutSettings → Logout → `logout_user()` (current id = None) → auth screen.
